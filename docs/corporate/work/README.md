# Дополнительные рабочие правила разработки 1С

Эти документы являются локальными дополнениями и не входят в исходный корпус
v8std. Общие стандарты 1С не копируются в этот раздел. Рабочие документы
фиксируют только область действия, правила проекта и уточнения, которых нет в
общем корпусе. Один набор можно использовать как общую командную политику и в
личных рабочих проектах.

- [Прозрачность типов для EDT](bsl-type-transparency.md)

- [Организация модулей и клиент-серверный код](module-organization.md)

## Что и когда попадает в контекст

Это описание доставки правил, а не новый нормативный документ. Оно не
индексируется для AI и не должно загружаться при каждой инженерной задаче.

Codex начинает с применимых `AGENTS.md` и каталога названий, описаний и путей
skills. Полный `SKILL.md` читается при выборе skill; связанные references —
при наступлении указанного в нём условия. Ссылка сама по себе не загружает
документ. См. официальные документы [Skills](https://learn.chatgpt.com/docs/build-skills)
и [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

| Этап | Нужный контекст | Что не загружается автоматически |
|---|---|---|
| Старт задачи | Применимые проектные ограничения, фиксированные roots/aliases, границы полномочий; каталог skills | Тела всех skills, весь corporate, все стандарты |
| Маршрутизация | `1c-routing` и skill текущего вопроса: index, platform, change, standards, BSL LS или YAxUnit | Соседние инструменты для повторного подтверждения того же факта |
| Цель дизайна, анализа соответствия или изменения установлена | Общий `1c-code-change/references/requirements.md` через standards/change skill; артефакт, операция, механизмы и нужные контракты | Нормы про отсутствующие механизмы; BSL baseline для metadata-only изменения |
| Подготовка решения | Полные подходящие подразделы corporate и общие стандарты по точным ID/ссылкам | Все связанные страницы рекурсивно; рекомендации из поиска как доказательство полноты |
| Ревью до применения | Фактический предлагаемый diff/selector, требования по обнаруженным в нём механизмам, baseline диагностик и защита от потери обновления | Повторная загрузка уже достаточных документов; перенос обязательной нормы на постфактум |
| После записи | Тот же набор требований, focused EDT diagnostics, необходимые проверки поведения | Новый «лучший» поиск вместо ранее выбранного контракта |

Первые три этапа не требуют загрузить весь перечень норм заранее. Но до выбора
решения или вывода о соответствии нужны все применимые к этому решению положения;
до записи — все применимые требования к фактическому изменению. Ревью до применения
проверяет не только исходную формулировку задачи, но и фактическое решение:
новый экспорт, дополнительный запрос, изменение контекста или транзакции
добавляют требования даже тогда, когда пользователь их не называл.

## Единица загрузки и совместимость

Сохранены семь стабильных ID `corporate:work:<document>:overview` и весь ранее
принятый нормативный текст. Подзаголовки `###` позволяют использовать существующий
`v8std_get_section` без изменения движка и без разбиения старого retrieval ID.
Замена их на `##` изменит состав индексных записей и требует миграции потребителей.

Пример точной выборки:

```json
{
  "id_or_alias_or_url": "corporate:work:query-conventions:overview",
  "heading": "Проверка наличия"
}
```

Это аргументы `v8std_get_section`; результат должен иметь `found=true` и
`body_truncated=false`. Заголовки здесь — часть контракта с Kafka/CRM skills.
При переименовании проверяйте их потребителей.

Для нескольких разделов одного короткого документа учитывайте не только размер
текста, но и количество вызовов: иногда одна полная компактная карточка дешевле
серии выборок. `v8std_get_summary(body_limit=6000)` пригоден как полный источник
только без усечения. При необходимости используйте полный `v8std_get_page` того
же документа. Полный документ покрывает его подразделы; их повторное чтение
не требуется.

`v8std_get_requirements_for_context` возвращает
`coverage=ranked_candidates_not_exhaustive`. Это поиск кандидатов, не сертификат
полноты требований. `summary` тоже не является семантическим резюме: это
ограниченный по длине body с компактными метаданными.

## Какие ссылки читать

Общие нормы остаются в исходном v8std; skill хранит селектор, а не копию норм.
Связанный стандарт читается, когда его механизм присутствует в изменении.
Например, для запроса проверки наличия нужен `std438`; `std436` добавляется
при запросах в цикле/пакетировании, `std725` — при потенциально неограниченном
результате. Само наличие ссылки на эти стандарты не требует загрузить все три
для любого изменения текста запроса.

При этом нельзя пропускать норму только потому, что её не было в пользовательском
описании. Селектор повторно применяется к фактическому изменению перед записью.
Неразрешённая применимость обязательного требования остаётся блокером.

## Результаты ревью corporate + skills

Исправлено в маршрутизации:

- Kafka одновременно требовала `corporate:work:*` и запрещала коллекцию
  `corporate` в audit-reference. Запрет заменён согласованной границей namespace.
- `1c-standards` и BSL LS имели слишком широкие триггеры для обычного изменения.
  Теперь они подключаются для своего вопроса; известные требования выбирает
  `1c-code-change` без дополнительного поиска.
- Полные страницы были единственным разрешённым доказательством даже при наличии
  компактного API. Добавлены точные подразделы и явная проверка полноты.
- В code-change теперь явно разделены inspection, выбор требований, ревью до
  применения и постпроверка. Review-only запрос не разрешает запись.
- YAxUnit использует компактные pattern/API карточки; BSL change review тестов
  также получает общие нормы, а запуск/чтение отчёта не загружает mutation gate.

Оставлено на отдельное содержательное согласование, без изменения принятых норм:

- Правило прозрачности типов ссылается на внешний документ `code_typification`.
  Его текст не входит в эту карточку: ссылка не равна локально полученному
  контракту. Если решение зависит от нераскрытого положения, применимость ещё
  не установлена.
- Формулировка о `&НаСервереБезКонтекста` не уточняет, что речь о выборе серверной
  процедуры, а не переводе всех методов формы на сервер. Контекст метода должен
  быть проверен до применения.
- Запрет менять тип переменной и обязательная локальная `Результат` — принятые
  локальные ограничения, а не универсальные свойства платформы. Исключения для
  составного/пустого результата и тривиальных функций требуют отдельного решения.
- В проектных AGENTS остаются повторяющиеся инструкции по tools, diagnostics,
  concurrency и YAxUnit. Их перенос способен уменьшить стартовый контекст, но
  это отдельная переработка принятых проектных инструкций; здесь она не выполнялась.

## Оценка эффективности

Измерение на 2026-09-03: объём `1c-code-change/SKILL.md` сокращён примерно на
41%, `1c-routing` — на 25–28%, `1c-standards` — на 12–13%. Это размеры текстов,
не измерение фактически оплаченных токенов. Новый reference селектора занимает
5040 символов и загружается только в соответствующей фазе; перенос в reference
сам по себе не делает суммарный контекст изменения меньше.

Для сценария локального присваивания и результата функции с литералами, без
изменения сигнатуры, запроса и ветвлений, JSON-ответы по четырём corporate
документам составляют: полные `get_page` — 13394 символа; полные compact bodies —
9177 (−31,5%, те же четыре вызова); точные разделы — 6988 (−47,8%, девять вызовов).
Замер использует один и тот же новый корпус и включает JSON-метаданные, но не
входы вызовов, общие стандарты, skills и рассуждение модели. Это иллюстрирует
компромисс объёма и числа вызовов, а не обещает такой процент экономии всей задачи.

Главный оставшийся фиксированный расход — проектные инструкции: versioned
Kafka `ai/AGENTS.md` около 16,6 КБ, CRM `PROJECT_AGENTS.md` около 11,5 КБ.
Сокращение skill-body не уменьшает уже загруженный AGENTS. Объём может отличаться
от активной установки до её штатного обновления.

## Проверка совместимости

После генерации локального индекса запускайте
`scripts/check_work_policy_skills.py --skills <Kafka skills root> --skills <CRM skills root>`.
Проверяются достижимость локальных и межскилловых references, разрешение corporate
selectors, общих стандартов и всех YAxUnit pattern IDs из таблицы маршрутизации.
`tests/test_knowledge_collections.py` проверяет полные старые ID,
точность и отсутствие усечения подразделов, а также приватность корпуса.

На 2026-09-03 прошли: структурная проверка 14 skills; 35 corporate selectors
и 27 standard IDs для каждого проекта; 20 тестов knowledge collections;
четыре статических suite CRM и три Kafka. Отдельное сравнение с HEAD подтвердило,
что после исключения новых заголовков нормативный текст семи страниц не изменён.

Полный Windows-прогон v8std: 253 теста, итог `failures=1, errors=6` вне изменённого
контура. Причины: отсутствие права создания symlink (повтор вне sandbox дал тот
же WinError 1314), отсутствующий заранее собранный `site`, недоступный исполняемый
файл в CLI-тесте, чтение UTF-8 через cp1251 и Unix-проверка mode 0644 на Windows.
Эти проверки не исправлялись в рамках оптимизации. Live-разработка/изменение 1С
и полноценный прогон поведенческих задач агентом не выполнялись: статическая
валидность селекторов сама по себе не доказывает качество каждого будущего решения.

Эта оптимизация не запускает установщики, не изменяет пользовательские копии
skills, проектные AGENTS вне репозиториев и работающие MCP. Для Docker-образа
новый корпус станет активным после отдельной сборки/развёртывания; Kafka-копии —
после штатной установки. CRM использует project-scoped ссылки на свои skills.

## Усиление применимости после анализа системных пропусков

Базовые коммиты до следующего этапа: v8std `23c3f40`, Kafka tools `1a656f3`,
CRM toolkit `ab8d19d`. Существовавшие правки примеров YAxUnit включены в базовый
коммит без пересмотра. Нормативные страницы на следующем этапе не менялись.

Исправлена не отдельная пара ID, а последовательность выбора и проверки:

- Короткое проектное правило действует до дизайна, анализа соответствия и
  изменения. Чистый поиск исходников исключён.
- Общий селектор учитывает свойства артефакта, операцию и фактические механизмы.
  Новый артефакт/полное ревью покрываются в запрошенном объёме; локальная правка
  требует только изменяемую часть и её окружающие инварианты. Outline достаточен
  вместо полного модуля, если нужен лишь контекст размещения.
- Отсутствие строки в таблице не означает отсутствия нормы. Требующиеся условия,
  исключения и нормативные зависимости догружаются; фоновые ссылки — нет.
- Загруженная страница не считается пройденной проверкой. В рабочем контексте
  связываются источник, проверяемая часть и результат; отдельный файл, подробный
  итоговый чек-лист или повторная загрузка не обязательны.
- Для YAxUnit область применения структурных/регистрационных/naming-паттернов
  больше не ограничена созданием нового модуля. Примеры не заменяют весь шаблон.
  Authoring gate применяется до записи; read-only review не требует запуска теста
  лишь для выдачи замечаний и не разрешает автоматически исправить их.

### Проверки и ограничение доказательств

В двух независимых read-only прогонах сравнивались базовая и изменённая версии:
дизайн транзакции, добавление теста/помощника, структурное ревью, локальный литерал,
появление файла/исключения, чистый поиск. Изменённая версия также проверена на
усечённом обязательном документе. Новая версия явно проводит дизайн к селектору,
структурное ревью — к контрактам существующего артефакта, расширение решения —
к дельте требований; чистый поиск не загружает нормы. Текстовый проект структуры
тестового модуля учитывает общие области, тестовый контракт и локального помощника.

Это не слепой статистический benchmark и не live-проверка EDT: контексты были
раздельными, но полнота чтения и формы текстовых результатов различались.
Нельзя выводить процент экономии токенов или отсутствие всех будущих пропусков.
В одном прогоне оценщик сам избыточно прочитал полный std455. Воспроизводимые
[сценарии и критерии](../../../tests/skill_context_scenarios.md) отделены от
постоянного контекста разработки. Дополнительный прогон H нашёл std642/std585
для фоновой операции и оповещения, хотя их нет в таблице: маршрут неизвестного
механизма сработал. В I обязательная структура применена вместо неполного примера.

Статически проходят 14 skills, 35 corporate selectors, 27 standards и 12 patterns
для каждого проекта; межскилловые ссылки разрешаются внутри соответствующего
репозитория. Тесты проверяют отказ на отсутствующем, усечённом или чужом pattern ID
и на reference, выходящем из каталога skills. Эти проверки не заменяют оценку
применения нормы к коду. Итоговые проверки: 23 теста knowledge collections,
три статических набора Kafka и четыре CRM прошли. Полный suite v8std на этом
этапе повторно не запускался; его прежние Windows-ограничения описаны выше.

прогонов до корректного результата со счётчиками токенов, включая исправления.

### Уточнение именования, согласованное пользователем

Исключение для тестовых модулей согласовано и закреплено в проектных инструкциях.
Полное правило хранится в [yaxunit:patterns:naming](../../yaxunit/patterns/naming.md),
без пересказа в навыках; замечание о конфликте CRM закрыто.

Замеры размеров выше относятся к этапу до этого уточнения именования.

Замечание о fluent-отступах закрыто: проверка в навыке уточнена по согласованному
принципу логической принадлежности, без вывода вложенности из возвращаемого типа.
Принятые примеры регистрации не изменялись.

Замечание о методах представления ошибки закрыто: по решению пользователя
локальное переопределение удалено из corporate; выбор методов задаёт std499.
Остальные содержательные замечания выше сохраняются.
