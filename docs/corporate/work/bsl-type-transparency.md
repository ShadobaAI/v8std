# Прозрачность типов BSL-кода для рабочих проектов

### Общий принцип

Новый и изменяемый код должен быть прозрачен для статического анализатора EDT.
Строгая типизация проверяет код при разработке и не меняет динамическую систему
типов при исполнении. Типизирующий комментарий не заменяет проверку значения.

### Контракты методов

Документируйте контракты по [#std453](../../std/453.md)
и [#std641](../../std/641.md). Для неэкспортного метода указывайте типы,
когда EDT не может надежно вывести их из прямого контекста вызова.
Для экспортных методов описывайте типы всех параметров и возвращаемых значений.
Ссылки на типы оформляйте по пункту 5.2.6 стандарта #std453; ссылка в тексте
пояснения не заменяет декларацию типа.

### Переменные

Применяйте требования EDT к
[типу и инициализации локальных переменных и переменных модуля](../../diagnostics/v8-code-style/variable-value-type.md)
и [изменению типа](../../diagnostics/v8-code-style/statement-type-change.md).
Не маскируйте несовместимые типы типизирующим комментарием.
Если алгоритм допускает несколько типов, проверяйте фактический тип перед
операциями, доступными только одному из них. Не объединяйте несвязанные типы
в одном контракте, например число и массив или строку и объект документа.

### Структуры и коллекции

Применяйте требования EDT к
[типам значений ключей](../../diagnostics/v8-code-style/structure-constructor-value-type.md),
[изменению состава структуры](../../diagnostics/v8-code-style/structure-key-modification.md)
и [типизации коллекций](../../diagnostics/v8-code-style/typed-value-adding-to-untyped-collection.md).
Добавляйте ключи в области видимости, где они затем используются;
в коллекциях не смешивайте несвязанные типы.

Для соответствия описывайте типы `Ключ` и `Значение` элемента `КлючИЗначение`
в возвращаемом значении функции-конструктора. Для списка значений указывайте
тип хранимых значений через `СписокЗначений из ...`. При передаче сложной
коллекции за пределы создающего метода используйте конструктор или получатель
с описанным возвращаемым значением.

### Табличные данные и конструкторы

Применяйте [#std641](../../std/641.md), включая исключение пункта 1.3,
и [#std453, пункт 5.2.2](../../std/453.md). Локальное дополнение: именуйте
функции-конструкторы `Новый...`, `Новая...`, `Новое...`.

Конструктор должен действительно создавать данные, а получатель — возвращать
их. Не создавайте фиктивные функции только ради ссылки на тип. Размещайте их
в модуле объекта или подсистемы, которой принадлежат данные. Экспортный
получатель может ссылаться на неэкспортный конструктор: открывать создание
пустого объекта через API для этого не требуется.

Строки таблиц и деревьев описывайте по [#std453, пункт 5.2.4](../../std/453.md).
Для общего механизма, работающего с частью объекта или формы, описывайте
используемые свойства и их типы. Свойства строк коллекции описывайте у типа
элемента, а не у самой коллекции. Не копируйте платформенный объект целиком
в структуру или таблицу без прикладной необходимости.

Для экспортной функции, возвращающей выборку или выгрузку запроса, описывайте
поля результата и их типы. Так же поступайте при динамическом тексте запроса,
если EDT не выводит состав результата. Отдельный пустой конструктор для такого
получателя не нужен.

### Универсальные контейнеры

После получения значения из временного хранилища или другого универсального
контейнера восстанавливайте тип ссылкой на функцию-конструктор или
функцию-получатель. Локальный типизирующий комментарий используйте только когда
тип нельзя сделать прозрачным структурой кода или ссылкой на конструктор.
Это относится и к дополнительным параметрам оповещений и СКД. Если универсальный
метод возвращает конкретный макет или объект XDTO, указывайте ссылку на его тип
в метаданных.

### Формы и именованные коллекции

Для конкретной формы указывайте в контракте полную ссылку на форму в метаданных.
Если общий код использует методы расширения формы, указывайте соответствующий
тип расширения. При получении известной формы передавайте ее полное имя
строковым литералом непосредственно в вызов, чтобы сохранить типизацию.
Порядок открытия и передачи параметров определяют [#std404](../../std/404.md)
и [#std741](../../std/741.md). Не передавайте всю структуру параметров открытия
одним параметром типа `Произвольный`.

К известному элементу именованной коллекции обращайтесь через точку:
`Элементы.Наименование`, а не `Элементы["Наименование"]`. Для программно
созданных элементов допустим строковый индекс с последующим уточнением типа
локальной переменной. Наличие необязательного элемента или свойства проверяйте
перед обращением.

Заменяйте реквизиты формы типа `Произвольный` реквизитами с определенными типами.
Исключение — данные общих библиотечных механизмов, которые сами обеспечивают
инициализацию и обработку. Если замена невозможна, инициализируйте значение
конструктором, получайте через типизированную функцию-получатель и проверяйте
допустимые типы. Учитывайте возможность передачи данных между клиентом и сервером.

### Проверка прозрачности типов

Проверяйте тип и доступные свойства в подсказке EDT и контекстном помощнике ввода.
При потере типа идите от первого объекта цепочки к его определению, затем
проверьте присваивания и передачи в методы до проблемного обращения.
Проверьте, что комментарий распознан как описание типа, а не обычный текст,
и что общий тип уточнен нужными свойствами. Исправляйте источник потери типа.

### Строгая типизация

Добавляйте `//@strict-types` в новые модули либо в существующие модули после их
полной адаптации. Не включайте строгую типизацию автоматически в legacy-модуле
ради локального изменения.
Аннотацию размещайте в заголовке до первой области, переменной или метода.
