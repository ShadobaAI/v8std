# Подготовка тестовых данных: независимость, повторный запуск и эталонная база

Основание: MainHelp 1.2.043.1, обзор подготовки данных и FAQ. Выбор способа хранения/подготовки — рекомендации, а контекст выполнения и отсутствие автоматического удаления описывают инструменты этой редакции. Восстановление и очистка базы зависят от правил конкретного окружения.

## Выбрать подход по стоимости независимого сценария

Цель — известное исходное состояние и воспроизводимая проверка, а не обязательное применение одного способа ко всем тестам.

| Подход | Когда полезен | Что нужно обеспечить |
| --- | --- | --- |
| Подготовка шагами сценария | Небольшой набор связных данных, который несложно создать | Независимость от порядка сценариев, уникальные признаки, явное поведение повторного запуска |
| Внешние файлы, JSON или макеты | Повторяемый более сложный набор, удобный для поддержки отдельно от действий UI | Версию, связи, проверяемую загрузку и совместимость с конфигурацией |
| Предзаполненная эталонная база/выгрузка | Большой связный массив или сложный интеграционный тест | Изолированное окружение, подтверждённую версию данных и отдельно разрешённый способ восстановления |

FAQ рекомендует стремиться к самостоятельной подготовке окружения сценарием, но признаёт стоимость и реальные комбинированные подходы. Для разных тест-кейсов одного проекта допустимы разные стратегии. Существующие записи не превращаются в fixture только потому, что их удобно выбрать.

## Сгенерировать подготовку и проверить её контекст

Инструмент «Подготовка и загрузка данных» позволяет отметить метаданные и сгенерировать feature-шаги создания данных. Альтернативный «Сериализатор макетов» сохраняет данные в специальных макетах. Это инструменты подготовки, а не подтверждение результата тестируемой операции.

Сгенерированные шаги создания данных выполняются на стороне **менеджера тестирования**. Если клиент подключён к другой базе, запись в менеджере не создаёт автоматически нужный объект у клиента. Поэтому место загрузки и целевой контекст проверки могут различаться.

Удаление созданных данных автоматически не производится. Владелец сценария определяет сохранение/очистку, включая результат после сбоя посередине. Данные одного сценария могут повлиять на другой: повторный запуск должен либо корректно использовать свои записи, либо создавать изолированный набор. См. [fixtures и идемпотентность](fixtures-idempotency.md).

## Хранить текстовые fixtures рядом с тестом, большие бинарники — осознанно

Генерирующие шаги и небольшие читаемые файлы данных можно версионировать вместе с тестами. Это связывает изменения данных с изменениями ожидаемого поведения. Файлы должны быть доступны из выбранного runtime; наличие в checkout само по себе этого не обеспечивает.

В учебном проекте маленькая DT-выгрузка в Git может упрощать одинаковую подготовку участников. FAQ подчёркивает, что для реальных больших баз бинарные выгрузки раздувают репозиторий и замедляют работу. Файловое/объектное хранилище либо менеджер бинарных артефактов — альтернативы; выбора конкретного сервиса этот recipe не навязывает.

Для любого хранилища нужны версия и способ доставки. Содержимое рабочей базы, credentials и случайные персональные данные не должны попадать в общие fixtures.

## Спланировать последовательность для нескольких баз

Vanessa допускает интеграционный сценарий с несколькими информационными базами и внешними сервисами. Рекомендация FAQ — сначала описать верхнеуровневую последовательность, затем вынести действия в [подсценарии](subscenarios-and-libraries.md).

В один момент один сценарий управляет только одним TestClient. Переключения и этапы интеграции идут последовательно; каждому клиенту соответствуют свои данные и профиль. Запуск обмена через UI либо программный шаг зависит от тест-кейса, но критерий проверки нужен для каждого значимого результата.

Если результат нужно проверить в базе клиента, используйте доступный для этого контекста механизм. FAQ приводит чтение состояния объекта через VAExtension для разных баз; запрос/шаг менеджера допустим для проверки клиентских данных только при доказанном общем или нужном маршруте базы.

## Независимость и повторный запуск

Независимость сценария определяется исходными объектами, правами, связями и поведением повторного запуска. Недостающая fixture, устаревший сценарий и дефект продукта имеют разные причины. Изменение ожидаемого результата не восстанавливает недостающие данные.

Способ восстановления эталона и очистки записей задаётся проектом: документация инструмента не определяет допустимые операции в произвольной базе. Связанные темы: [диагностика выполнения](execution-debugging.md), [классификация ошибок](failure-classification.md).
